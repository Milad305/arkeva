## ۱. هدف و مشکل دنیای واقعی

در بوم، هشدار در شش صفحه پراکنده است و هر کدام قاعدهٔ خودش را دارد. این فایل **یک رجیستری** از قواعد می‌سازد: هر هشدار کد، شرط، مخاطب، راهنما و لینک اقدام دارد (اصل ۳ نمای کلی). صفحه‌ها فقط جدول `Alert` را می‌خوانند.

## ۲. مدل ارزیابی

### ۲.۱ تعریف قاعده (در کد)
```
AlertRule {
  code            'AL-PRG-01'
  subjectType     wbs_item | cbs_item | project | user_in_project | risk | integration
  triggers        [event types] یا [DailyTick | HourlyTick]
  params          { key: {type, default, min, max, unit} }
  evaluate(ctx)   → [{subjectId, severity | null, values{}}]   // null = شرط برقرار نیست
  audience(ctx)   → [{userId, via: role|owner|supervisor|approver}]
  guidance        قالب متن با {placeholder}
  actionLink      قالب مسیر
}
```
قاعده خالص است: فقط از جدول‌های مشتق و واقعیت‌ها می‌خواند و جایی نمی‌نویسد.

### ۲.۲ چرخهٔ هشدار (D09)
`open` ← `seen` ← `resolved` (خودکار) یا `dismissed` (دستی با دلیل).
- **کلید یکتا:** `ruleCode:subjectType:subjectId`، تا وقتی `open` یا `seen` است، نمونهٔ تازه ساخته نمی‌شود؛ فقط `payload` و `lastEvaluatedAt` به‌روز می‌شود.
- **ارتقا:** اگر شدت از `warning` به `critical` برسد، همان هشدار ارتقا می‌یابد و **یک اعلان تازه** می‌سازد. کاهش شدت اعلان نمی‌سازد.
- **رفع خودکار:** وقتی `evaluate` دیگر چیزی برنمی‌گرداند ← `resolved`.
- **بازگشایی:** اگر شرط در ۲۴ ساعت پس از رفع دوباره برقرار شود، همان هشدار دوباره `open` می‌شود و اعلان جدید نمی‌سازد. `[تأییدشده]`
- **ردِ دستی (`dismissed`):** فقط مدیر پروژه و فقط با دلیل؛ تا وقتی شرط رفع نشده و دوباره برقرار نشود دوباره باز نمی‌شود. هشدارهای `critical` ردپذیر نیستند. `[تأییدشده]`
- **مرتبط‌سازی با اعلان:** هر هشدار برای هر گیرنده حداکثر یک اعلان در هر کانال می‌سازد (F13، بخش تکرار).

### ۲.۳ زمان ارزیابی
| منبع | رفتار |
|---|---|
| رویداد | پس از `ComputeFinished` یا انتشار رویداد غیرمحاسباتی؛ فقط قواعد مرتبط با آن رویداد (ماتریس ج) و فقط برای پروژهٔ همان رویداد |
| `HourlyTick` | AL-APR-01 |
| `DailyTick` | قواعد زمانی (ماتریس ج) |
| بازسازی پس از خرابی | اجرای کامل همهٔ قواعد برای پروژه (فرمان ادمین) |

### ۲.۴ پارامترها (بستن G8)
- سه سطح: پیش‌فرض کد ← پیش‌فرض سازمان ← تنظیم پروژه (`AlertRuleSetting`). نزدیک‌ترین سطح برنده است.
- کاربر قاعده را روشن/خاموش می‌کند و پارامترهایش را عوض می‌کند. قاعده‌ساز کاربری نیست (D09).
- خاموش کردن قاعده، هشدارهای بازش را `resolved` می‌کند با دلیل «قاعده غیرفعال شد».
- قواعد `AL-INT-01` و `AL-STR-06` غیرقابل‌خاموش‌اند. `[تأییدشده]`
- **صفحه:** بخش «قواعد هشدار» در W30 (جدول: کد، نام، روشن، پارامترها، شدت). ویرایش با `alerts.configure`.

### ۲.۵ تعیین مخاطب
مخاطب از نقش در همان پروژه و رابطه با موضوع ساخته می‌شود (نه فهرست ثابت کاربر):

| مخاطب | معنی |
|---|---|
| `pm` | مدیر پروژه |
| `planner` | کاربران با نقش برنامه‌ریز |
| `finance` | کاربران با دسترسی `cost.view` و نقش مالی |
| `supervisor` | سرپرست آن آیتم |
| `approver` | تأییدکنندهٔ مرحلهٔ مربوط (و جایگزین، پس از مهلت) |
| `owner` | مالک ریسک یا اقدام |
| `org_admin` | مدیر سازمان |

مخاطبی که دسترسی دیدن موضوع را ندارد، اعلان نمی‌گیرد (مثلاً بدون `cbs.view_amounts` متن مبلغ ندارد).

## ۴. مثال طلایی (تست پذیرش)
برای مثال مرجع و مثال CBS، با پیش‌فرض‌ها، ارزیابی پس از آخرین بازمحاسبه دقیقاً این هشدارها را می‌سازد:

| کد | موضوع | شدت |
|---|---|---|
| AL-PRG-01 | برگ 1.1.2 (d=−10) | warning |
| AL-PRG-01 | برگ 1.2.1 (d=−10) | warning |
| AL-PRG-02 | پروژه (d=−5.8) | warning |
| AL-PRG-03 | پروژه (تأخیر ۱۴ روز کاری، با فیکسچر F11 ۶.۱) | warning |
| AL-CST-01 | قلم C1 (105٪) | warning |
| AL-CST-02 | اقلام C1، C2، C3 | warning |
| AL-CST-04 | پروژه (CPI=0.9423) | warning |

**هشدار نباید بسازد:** AL-CST-03 (اختلاف ۳ واحد)، AL-X-01 (هیچ آیتمی critical نیست)، و AL-PRG-01 برای والدهای 1.1 و 1.2.

## ۵. اعلان‌ها از هشدار
- هشدار جدید یا ارتقاءیافته ← رویداد `AlertRaised` ← F13 برای هر مخاطب و کانال طبق ماتریس.
- رفع هشدار اعلان نمی‌سازد، فقط در پنل وضعیتش به «رفع‌شده» عوض می‌شود.
- نمایش: `Alert.guidance` با مقدارهای لحظهٔ ارزیابی ساخته و ذخیره می‌شود؛ تغییر قالب بعدی هشدارهای باز را عوض نمی‌کند.
